# PRD: Author Persona System

> Persistent, story-scoped author persona injected as a system prompt across generative pipeline stages to improve voice consistency, stylistic fidelity, and thematic coherence in long-form story generation.

**Date:** 2026-05-08
**Author:** Planner agent
**Status:** Draft

## Problem Statement

The llm-story-writer pipeline currently dispatches each generation call (outline expansion, chapter writing, scene writing, prose scrubbing, final editing) without any persistent author identity. Every call relies on the user-prompt task instructions to encode style, voice, and thematic preferences. The `_llm.generate_text` infrastructure supports a `system_message` parameter, but no tool actually populates it. As a result, the model defaults to a generic "average author" voice that drifts across chapters, mixes registers between scenes, and produces structurally neutral outlines that the chapter-writer then has to override stylistically.

This is a recognised problem class. The 2025 paper "Whose Story Is It?" (Yang et al., arXiv:2502.13028) demonstrates a 5–14 point improvement on stylistic faithfulness metrics when a structured author persona is injected into the system prompt, with strongest gains in voice, diction, and creativity dimensions. Production tools (Sudowrite Story Bible, NovelAI Memory/Author's Note) treat persistent author identity as a first-class control surface. Multi-model research synthesis (see [.github/research/author-persona-system-prompts-2026-05-08.md](../../.github/research/author-persona-system-prompts-2026-05-08.md)) reached unanimous agreement across three independent LLM researchers on six core findings supporting this feature.

The pipeline already produces the raw material for a persona during outline analysis: the eight analysis chunks generated by `outline-generator analyze-prompt` include `tone_style` and `theme_message`, both of which describe the intended voice. This information is captured during planning and then effectively discarded — it never reaches the chapter-writer or scrubber as a persistent system-level constraint.

## Goals

1. Generate a structured Author Persona artefact during story initialisation, derived from the existing `tone_style`, `theme_message`, and `core_story_foundation` analysis chunks.
2. Produce four agent-specific persona views (outline, chapter, scrubber, editor) from a single source of truth.
3. Inject the appropriate persona view as a `system_message` on every generative LLM call across the affected agents.
4. Re-inject the persona on every call (do not rely on conversation history) to mitigate persona drift.
5. Achieve measurable improvement in voice consistency across chapters in subjective comparison testing on a baseline story.

## Non-Goals

- **Plot coherence enforcement.** The persona must not be asked to enforce event ordering, entity consistency, or cause-effect chains. Those remain with the wiki, recap, and savepoint systems. (Confirmed by Yang et al. results: persona gains are weakest in the "Plot" dimension.)
- **Dynamically evolving personas.** The persona is static for the story's lifetime. No published evidence supports evolving the persona as the manuscript matures.
- **Author name imitation.** The persona describes traits explicitly, not by reference to named authors ("write like Hemingway"). This is both technically more reliable and ethically cleaner.
- **Application to analytical agents.** The `consistency-checker` and structural sub-phases of the outline-planner receive no persona framing. Persona prompts measurably degrade factual reasoning tasks (Kim et al., arXiv:2408.08631).
- **Style sample injection.** Pasting 3–5 pages of reference prose into every call (Sudowrite-style) is out of scope for v1 — token cost is prohibitive for local-model deployments. Could be revisited later.
- **Replacement of existing tone/theme analysis chunks.** Those remain the upstream source; the persona is a downstream derivation.

## User Stories

### Story author (CLI user)

- As a story author, I want the pipeline to maintain a consistent narrative voice across all chapters so that the finished manuscript reads like one author wrote it, not three.
- As a story author, I want genre-specific stylistic decisions (sentence rhythm, dialogue register, pacing) to persist across the entire pipeline without me having to re-specify them per chapter.
- As a story author, I want to inspect and optionally edit the generated persona before chapter generation begins so that I can correct misinterpretations of my prompt.

### Pipeline maintainer (developer)

- As a pipeline maintainer, I want a single canonical persona document with deterministic agent-specific views so that I do not duplicate stylistic information across multiple files.
- As a pipeline maintainer, I want persona injection to be opt-in via configuration so that existing stories generated without personas remain reproducible.

## Proposed Solution

### Architecture Overview

A new pipeline phase — **persona generation** — runs once per story between `generate-elements` (Phase 2 of outline-planner) and outline expansion (Phase 3). The phase produces a structured Author Persona document stored at `stories/<name>/persona/persona.md`. Four agent-specific views are derived deterministically from this document and stored under `stories/<name>/persona/views/`. Every generative tool call across affected agents loads the appropriate view and passes it as the `system_message` parameter to `_llm.generate_text`.

The persona is **static** for the story's lifetime. Per-chapter and per-scene adaptation comes from a short "emphasis delta" passed in the user prompt by the chapter-writer agent — not from modifying the persona.

### Persona Document Structure

The canonical persona is a Markdown file with YAML frontmatter:

- **Frontmatter**: genre, subgenre, POV, tense, generated_from (savepoint references), created_at
- **Identity paragraph** (50–100 words, second-person): a concise statement of the author's overall stance
- **Five trait dimensions** (each 30–60 words):
  - Prose texture (sentence length, vocabulary register, sensory emphasis, metaphor habit)
  - Dialogue style (register, subtext level, attribution style, idiom)
  - Pacing philosophy (scene-to-summary ratio, action density, introspection density)
  - Thematic sensibility (preoccupations, moral framework, what this author never does)
  - Narrative philosophy (POV stance, interiority depth, conflict approach, resolution style)
- **Anti-pattern bullets** (5–10 short rules): things the author specifically avoids

Total target length: configurable via `generation.persona_word_budget` (default `225`, target window 200–250 words). This is consistent with the Yang et al. Author Writing Sheet evidence (~300 words) and avoids token bloat that would dilute attention. Smaller local models can be tuned down to ~150 words; frontier models can be tuned up to ~350.

### Agent Views

Four projections derived from the canonical persona:

| View | Recipients | Contents |
|------|------------|----------|
| `views/outline.md` | outline-planner (generation phases only — not analytical sub-phases) | Identity paragraph, narrative philosophy, thematic sensibility, pacing philosophy, anti-patterns. **Excludes** prose texture and dialogue style. |
| `views/chapter.md` | chapter-writer, scene-writer | Full persona — all five trait dimensions, identity paragraph, anti-patterns. |
| `views/scrubber.md` | prose-scrubber | Identity paragraph (one sentence), prose texture, dialogue style, anti-patterns. **Excludes** pacing, thematic sensibility, narrative philosophy. |
| `views/editor.md` | final-editor | Identity paragraph, prose texture, dialogue style, narrative philosophy (voice-relevant subset), anti-patterns. |

The `consistency-checker` receives **no persona view**. The outline-planner's structural analysis sub-phases (`analyze-prompt`, `generate-elements`) receive no view — the persona does not yet exist during those phases anyway.

### Persona Generation

A new tool `persona-builder` exposes operations:

- `generate` — read `core_story_foundation`, `tone_style`, `theme_message`, and `story_elements` savepoints; call LLM with a structured generation prompt; produce the canonical persona document.
- `get-view <view-name>` — read the canonical persona and return the requested agent view as plain text (suitable for inline use in `system_message`). Views are derived on read, not stored as separate files (eliminates drift between source and views).
- `regenerate` — re-run generation, archiving the previous version.

A skip flag in config (`generation.enable_author_persona: bool`) controls whether this phase runs. Default: `true` for new stories, but the chapter-writer and other agents must gracefully degrade to no-system-prompt behaviour when the persona is absent (so existing stories remain compatible).

### Integration Points

The persona is injected via `system_message` at every generative call. Affected files:

| Tool / agent | Current state | Integration |
|---|---|---|
| `outline-generator` (expand-chapter, refine-chapter, etc.) | Uses `_call_llm(prompt, model=...)` without system_message | Accept optional `--persona-view outline` CLI argument; load view via `persona-builder get-view`; pass as `system_message` |
| `scene-writer` (generate, revise, scrub-analyze, voice-analyze) | Same | Accept optional `--persona-view chapter\|scrubber\|editor`; pass as `system_message` |
| `recap-manager` | Same | **No persona** — recap generation is summarisation, not creative voice work |
| `critique-runner` | Same | **No persona** — analytical agent |
| `chapter-writer.md`, `outline-planner.md`, `prose-scrubber.md`, `final-editor.md` agent prompts | No persona awareness | Updated to call `persona-builder get-view` before tool dispatch and pass the view via the new CLI argument |
| `story-orchestrator.md` | No persona phase | New phase between outline elements generation and outline expansion |

### Storage

```
stories/<name>/persona/
  persona.md              # canonical document with frontmatter
  history/                # archived previous versions on regenerate
    persona-YYYYMMDD-HHMMSS.md
```

A savepoint (`step: "persona"`) stores a JSON pointer to the persona path for resumability and pipeline state tracking.

### Backend

- New tool `src/tools/persona_builder.py` — generation, view derivation, history management
- New OpenCode wrapper `.opencode/tools/persona-builder.ts` (if OpenCode runtime is in use) — not strictly required for v1 since direct CLI invocation works
- Modifications to `src/tools/outline_generator.py` and `src/tools/scene_writer.py` to accept and forward `system_message`
- New prompt template `prompts/agents/persona-builder.md` (or `prompts/persona/generate.md`) — second-person structured generation prompt

### Frontend

CLI changes only:

- `outline-generator` and `scene-writer` accept an optional `--persona-view` argument
- `persona-builder` is a new CLI tool
- Story-orchestrator agent prompt gains a new phase invocation

No TUI/UI changes in v1. Inspection of the persona is done via opening `stories/<name>/persona/persona.md` directly.

### Database

No ChromaDB or persistent database changes. Personas live as Markdown on disk alongside other story artefacts. The wiki collections are unaffected.

### Configuration

New `config.yml` settings under `generation`:

```yaml
generation:
  enable_author_persona: true
  persona_model: "openai-compat://..."   # falls back to creative_model if unset
  persona_word_budget: 225               # target word count for the canonical persona document; valid range 100–500
  enable_emphasis_delta: true            # per-chapter tonal adjustment alongside the static persona
```

## Acceptance Criteria

- [ ] `persona-builder generate` produces a valid persona document at `stories/<name>/persona/persona.md` with required frontmatter and all five trait dimensions
- [ ] Generation prompt honours `persona_word_budget` config; output word count falls within ±20% of the target
- [ ] `persona-builder get-view chapter` returns the full persona view as plain text on stdout
- [ ] `persona-builder get-view outline` returns a view that **excludes** prose-texture and dialogue-style sections
- [ ] `persona-builder get-view scrubber` returns a view that **excludes** pacing, thematic, and narrative-philosophy sections
- [ ] `outline-generator expand-chapter --persona-view outline` passes the view text as `system_message` (verified via `LLM_DEBUG_LOG` containing the system message in the recorded JSONL record)
- [ ] `scene-writer generate --persona-view chapter` passes the chapter view as `system_message` (same verification)
- [ ] `scene-writer generate --emphasis-delta "<text>"` injects the delta phrase into the user prompt (verified via debug log)
- [ ] Per-chapter emphasis delta is auto-derived from the chapter outline (e.g., chapter tone/beat label) and forwarded by the chapter-writer agent
- [ ] `consistency-checker` receives no persona view (verified by inspection of agent prompt and absence of persona injection in its tool calls)
- [ ] Story generation with `enable_author_persona: false` produces identical behaviour to current pipeline (no persona injected anywhere)
- [ ] Story generation with `enable_author_persona: true` and a missing persona file (e.g., legacy story) does not crash — agents pass `system_message=None` and continue
- [ ] `enable_emphasis_delta: false` disables the per-chapter delta without affecting the static persona
- [ ] Re-generation via `persona-builder regenerate` archives the previous persona to `history/` with a timestamp
- [ ] Subjective comparison: generate the same chapter for the same story prompt with and without persona; the with-persona output preserves voice traits described in the persona document (manual review on a sample story)

## Resolved Decisions

- **Persona generation owner:** the **outline-planner** sub-agent invokes `persona-builder generate` immediately after `generate-elements`. The story-orchestrator does not own the call directly; it dispatches outline-planner, which performs the generation as part of its normal workflow.
- **View derivation:** views are derived at read time (no separate view files persisted). Single source of truth.
- **Emphasis delta in v1:** the per-chapter "emphasis delta" pattern is **included in v1**. The chapter-writer accepts an optional emphasis-delta string in the user prompt for each chapter, drawn from the chapter outline (e.g., a chapter labelled "elegy" or "climax" produces a short delta phrase). This rides alongside the static persona and provides chapter-local tonal adjustment without modifying the persona itself.
- **Persona length budget is configurable.** Default `persona_word_budget: 225` (target window 200–250 words). The generation prompt template is parameterised on this budget so smaller local models can be tightened to ~150 words without code changes.
