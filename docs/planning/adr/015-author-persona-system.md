# ADR 015: Author Persona System

**Date:** 2026-05-08
**Status:** Proposed

## Context

The llm-story-writer pipeline dispatches every generative LLM call (outline expansion, chapter writing, scene writing, prose scrubbing, final editing) without populating the `system_message` parameter that `_llm.generate_text` already supports. The model defaults to a generic "average author" voice that drifts across chapters, mixes registers between scenes, and produces structurally neutral outlines that downstream agents must override stylistically.

The pipeline already produces the raw material for an author persona during outline analysis — the eight analysis chunks generated by `outline-generator analyze-prompt` include `tone_style`, `theme_message`, and `core_story_foundation`. This information is captured during planning and effectively discarded, never reaching downstream agents as a persistent system-level constraint.

A multi-model research synthesis (see [.github/research/author-persona-system-prompts-2026-05-08.md](../../../.github/research/author-persona-system-prompts-2026-05-08.md)) reached unanimous agreement across three independent LLM researchers on the value of injecting a structured author persona as a system prompt. The strongest evidence is Yang et al. (2025) "Whose Story Is It?" (arXiv:2502.13028), which demonstrates a 5–14 point improvement on stylistic faithfulness metrics with a structured Author Writing Sheet injected into the system prompt.

The architectural question is not whether to add a persona layer, but how it should be structured, where it should live, and which agents should receive it.

## Decision

Implement an **Author Persona** as a story-scoped, static, structured Markdown document with deterministically-derived agent-specific views, injected as `system_message` on every generative LLM call across the affected pipeline stages.

Specific architectural commitments:

1. **One canonical document, multiple views.** A single `stories/<name>/persona/persona.md` file is the source of truth. Four agent-specific views (`outline`, `chapter`, `scrubber`, `editor`) are derived deterministically at read time. Views are never persisted as separate files — this eliminates the risk of stale views drifting from the source.

2. **Static for the story's lifetime, with a per-chapter emphasis delta in v1.** The persona itself is generated once during story initialisation, immediately after the outline-elements phase, and is not updated as the manuscript evolves. Per-chapter stylistic variation comes from a short "emphasis delta" string — derived from chapter outline metadata (tone label, beat, arc position) and appended to the user prompt by the chapter-writer. The delta does not modify the persona; it rides alongside it. Both the persona and the emphasis delta are independently configurable.

3. **Persona generation owned by `outline-planner`.** The story-orchestrator does not invoke `persona-builder` directly. The outline-planner sub-agent calls it as a workflow step immediately after `generate-elements`, since outline-planner already owns the analysis chunks (`tone_style`, `theme_message`, `core_story_foundation`) the persona is derived from. This keeps generation logic adjacent to its inputs and avoids cross-agent state plumbing.

4. **Configurable word budget.** The persona target length is controlled by `generation.persona_word_budget` (default `225`, valid range 100–500). The generation prompt is parameterised on this value, so smaller local models can be tightened to ~150 words and frontier models loosened to ~350 without code changes.

5. **Injection via `system_message`, re-applied per call.** The persona view is passed as the `system_message` parameter on every generative call. Conversation history is never relied upon to carry the persona — every call is stateless from the persona's perspective. This mitigates persona drift documented at 10–16-turn horizons.

6. **Generative agents only — never analytical.** The persona is applied to:
   - `outline-generator` (outline expansion / refinement operations)
   - `scene-writer` (`generate`, `revise` operations)
   It is **never** applied to:
   - `consistency-checker`
   - `recap-manager`
   - `critique-runner`
   - `outline-generator` analytical sub-phases (`analyze-prompt`, `generate-elements`)
   - `scene-writer` analytical operations (`parse-definitions`, `assemble-chapter`, `scrub-analyze`, `voice-analyze`)

   This restriction is grounded in Kim et al. (2025) "Persona is a Double-edged Sword" (arXiv:2408.08631), which demonstrates persona prompts measurably degrade factual reasoning tasks.

7. **LLM-generated, not hand-authored.** The persona is generated by the LLM from the existing `tone_style`, `theme_message`, `core_story_foundation`, and `story_elements` analysis chunks. Hand-authoring is supported (the user can edit the file before chapter generation) but is not the default path. Kim et al. show LLM-generated personas outperform handcrafted ones in benchmark evaluation.

8. **Parallel to the wiki, not part of it.** The wiki holds factual entity information and is the source of truth for who/what/where (per ADR 014). The persona holds stylistic and authorial-decision information and is the source of truth for how the story is told. The two systems are complementary and live in separate directories under `stories/<name>/`.

9. **Opt-out via configuration with graceful degradation.** Two independent flags:
   - `generation.enable_author_persona: bool` (default `true`) controls the static persona generation and `--persona-view` injection.
   - `generation.enable_emphasis_delta: bool` (default `true`) controls the per-chapter delta independently.

   When either flag is `false`, the corresponding behaviour is suppressed cleanly. Agents must also gracefully degrade when the persona file is absent (legacy stories) — `persona-builder get-view` returns empty stdout, and tools treat empty as "no system message."

## Consequences

### Positive

- Voice and stylistic consistency improve measurably across long-form generation, anchored by published academic evidence (~5–14 point gain on faithfulness metrics).
- Agent-specific views right-size the persona for each pipeline stage — the prose-scrubber gets sentence-level rules only, the outline-planner gets narrative philosophy only — reducing token waste and attention dilution.
- The architecture is drop-in compatible with the existing tool/agent pattern (ADR 001) — one new tool, one new prompt template, parameter additions to existing tools.
- Single source of truth + read-time derivation eliminates the multi-file drift risk that would arise if views were persisted separately.
- The configuration flag and graceful-degradation contract preserve reproducibility for stories generated under the pre-persona pipeline.

### Negative

- Every generative call gains 200–350 tokens of system message overhead. At 16k context length and the current chapter-writer scene-generation budget, this is well within margin, but smaller models or tighter budgets may need a `persona_max_tokens` knob in v2.
- The agent prompt files for the orchestrator, outline-planner, chapter-writer, prose-scrubber, and final-editor must all be updated. This is a wide change surface and a regression risk for ongoing pipeline work.
- Persona quality depends on LLM generation quality. A poor persona will produce systematically worse output across the entire story than no persona at all — the user-facing inspection-and-edit loop is therefore essential, not optional.
- Local 7B–26B quantised models (the default deployment target) may not benefit from persona anchoring as strongly as the GPT-4-class models in the academic evidence base. This is an empirical risk that can only be assessed by subjective comparison testing.

### Neutral

- The persona document format is decoupled from the wiki page format. They share Markdown + YAML frontmatter conventions but have different schemas and lifecycles.
- `recap-manager` does not receive a persona view in v1. This is a deliberate choice — recap generation is summarisation, not creative voice work. Could be revisited if recap voice drift is observed.
- The emphasis-delta source (chapter outline metadata) is currently best-effort: chapter outlines do not have a strict tone/beat schema, so the chapter-writer derives the delta heuristically from available labels. A future enhancement could add structured tone fields to the chapter outline schema.
