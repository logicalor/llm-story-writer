# ADR 005: Hybrid Wiki Context Retrieval and Synthesis Pipeline

**Date:** 2026-04-12
**Status:** Proposed

## Context

ADR 004 established the progressive wiki memory system — a structured, LLM-maintained knowledge base that grows alongside the story. That decision introduced a `wiki-snapshot` tool to assemble pre-generation context from wiki pages, but left the retrieval and synthesis mechanism underspecified.

The core challenge: given a scene outline and a wiki containing ~100-500 structured pages, how do we **efficiently search, select, and assemble** the right pages into a coherent ~15K-token context payload for the generation prompt?

Naive approaches (concatenating all pages, single semantic search query, manual page selection) all fail at scale:
- **Full concatenation** exceeds the token budget by 10-50x
- **Single semantic query** misses narratively relevant pages that are semantically dissimilar to the scene (a character page is "relevant" because the character appears in the scene, not because its embedding is near the scene outline)
- **Manual selection** doesn't scale beyond a few chapters

Multi-model research ([retrieval/synthesis report](../../.github/research/wiki-context-search-synthesis-2026-04-12.md) — Claude, GPT, Gemini consensus) unanimously confirmed that entity mention matching is the primary retrieval signal for narrative context, not semantic similarity. Research also showed that synthesized context significantly outperforms raw concatenation: CASC demonstrates +42% coherence improvement, Oreo achieves +7% accuracy with 12.87x token reduction, and RECOMP achieves 6% compression rate with minimal quality loss.

## Decision

Implement a **three-stage hybrid retrieval and context assembly pipeline** in the `wiki-snapshot` tool, combining deterministic entity matching, structured metadata queries, semantic search, and wikilink graph traversal — with pre-computed hierarchical detail levels and delta caching.

### Stage 1: Hybrid Multi-Tier Retrieval

Four retrieval tiers run sequentially, with results merged via Reciprocal Rank Fusion (RRF):

| Tier | Method | Priority | Signal |
|------|--------|----------|--------|
| T1 | Deterministic entity matching | HIGHEST | Entity name or alias appears in scene outline |
| T2 | Metadata-filtered ChromaDB query | HIGH | Frontmatter fields match (e.g., `type=plot_thread, status=active`) |
| T3 | Semantic vector search | SUPPLEMENTARY | Scene outline embedding ↔ page embedding cosine similarity |
| T4 | Wikilink graph traversal (1-2 hop) | MEDIUM | Pages linked from T1/T2/T3 results (max 5 additional) |

T1 is the foundational tier: the wiki index maintains a complete name → slug mapping (including aliases from frontmatter), enabling O(1) deterministic lookup. This matches how NovelCrafter Codex and NovelAI Lorebook work in production — keyword-triggered entry injection.

T4 exploits the wiki's existing [[wikilinks]] as a lightweight knowledge graph, providing the relationship-aware retrieval benefits of GraphRAG/LightRAG without the expensive graph construction step. Full GraphRAG is explicitly rejected as overkill for ~200-500 structured pages (2.3x latency, 13.4% accuracy regression on factual queries vs. vanilla RAG).

**Relevance scoring** for each retrieved page:

```
score(p) = 0.40 × entity_match(p)
         + 0.20 × wikilink_proximity(p)
         + 0.20 × semantic_similarity(p)
         + 0.10 × recency(p)
         + 0.10 × type_priority(p)
```

Pages scoring below 0.15 are dropped.

### Stage 2: Detail Level Selection & Token Budgeting

Every wiki page has pre-computed content at three detail levels (generated by the wiki-maintainer when pages are created/updated):

| Level | Name | Tokens | Use Case |
|-------|------|--------|----------|
| L1 | Headline | ~30 | Background entities, budget overflow fallback |
| L2 | Brief | ~150 | Secondary scene characters, supporting context |
| L3 | Full | ~500 | POV character, primary location, central plot thread |

Pages are sorted by relevance score and assigned detail levels top-down within the ~15K token budget:
- **Protected tier** (POV character, primary location): always L3, never demoted
- **High-priority** (scene characters, active plot threads): L3 when budget allows, L2 when tight
- **Medium-priority** (world rules, related entities from graph traversal): L2 default
- **Low-priority** (themes, distant relationships): L1

When total exceeds budget, lower-priority pages demote L3→L2→L1 starting from the bottom of the ranked list. Pages are never dropped entirely — minimum L1 ensures the generation LLM is at least aware of every relevant entity's existence.

Scene-type adaptation adjusts allocation: dialogue-heavy scenes shift budget toward character profiles + relationships; action scenes shift toward world rules + location details; first-appearance scenes allocate L3 to new entities regardless of computed priority.

### Stage 3: Structured Context Assembly

**Default: Deterministic template assembly.** Pages are loaded at their assigned detail level and assembled into a fixed-structure markdown document:

```markdown
## Scene Context
### Characters
[POV character — L3 full profile]
[Scene characters — L2/L3 brief/full profiles]
[Background characters — L1 headlines]
### Location
[Current location — L3 full description]
### Active Plot Threads
[Relevant threads — L2 brief descriptions]
### World Rules
[Applicable rules — L2 brief descriptions]
### Recent Events
[Last 2-3 timeline entries]
### Relationships
[Between scene characters — L1/L2 descriptions]
```

**Optional: LLM synthesis pass.** For complex scenes (>5 characters or >3 active plot threads, or first scene in a chapter), the assembled document is passed through the 7b maintenance model with a synthesis prompt that instructs: "Restructure and condense the following context into a coherent scene brief. You may reorder, merge related facts, and remove redundancy. You must NOT add any information not present in the source material." This is opt-in because the risk of synthesis hallucination exists and deterministic assembly is sufficient for most scenes.

### Delta Caching

Consecutive scenes within a chapter share 60-90% of their context (same characters, same location, same active plot threads). A scene-level cache avoids redundant retrieval:

1. Compare current scene's entity set to previous scene's entity set
2. **Kept entities**: check page `version` counter — if unchanged since last retrieval, reuse cached content verbatim; if bumped by wiki-update, re-fetch
3. **New entities**: full retrieval + scoring + detail level assignment
4. **Removed entities**: drop from cache
5. **Always refresh**: recent timeline entries (new events from prior scene)
6. **Chapter boundaries**: invalidate entire scene cache (new timeline position, potentially new location/characters)

Target cache hit rate: >60% for consecutive scenes in the same chapter.

## Consequences

### Positive

- **Entity mention matching (T1) provides guaranteed recall** for explicitly named entities — the most important context for narrative consistency
- **Hybrid retrieval catches all relevance dimensions**: explicit mentions (T1), structural relationships (T2), thematic relevance (T3), and relationship-based discovery (T4)
- **Pre-computed detail levels eliminate retrieval-time summarization** — no LLM calls needed to compress pages when token budget is tight
- **Delta caching eliminates 60-90% of retrieval work** for consecutive scenes — significant performance improvement for 100+ scene novels
- **Deterministic default assembly is fast, reproducible, and hallucination-free** — the LLM synthesis pass is opt-in for complex scenes only
- **Graceful degradation** — pages demote L3→L2→L1 rather than being dropped, so the generation LLM always knows what entities exist even when budget is tight

### Negative

- **Complexity**: the three-stage pipeline with four retrieval tiers, relevance scoring, detail level selection, and delta caching is substantially more complex than naive concatenation or single-query retrieval
- **Relevance weights are unvalidated**: the 0.40/0.20/0.20/0.10/0.10 weights are reasoned from first principles and cross-model consensus but require empirical tuning against actual generated stories
- **nomic-embed-text fiction domain gap**: no specific benchmarks exist for nomic-embed-text on fictional/narrative content — T3 semantic search quality is uncertain for fantasy names, invented locations, and genre-specific terminology
- **Wikilink graph density risk**: heavily-interlinked wikis could cause T4 to return too many results despite the max-5 cap; the cap itself may need tuning per story
- **Optional LLM synthesis pass carries hallucination risk**: if the 7b model adds information not in the source pages, it introduces factual errors; this is mitigated by making it opt-in and instruction-constrained

### Neutral

- The relevance scoring formula is explicitly designed for tuning — all weights are configurable, and a future task could implement a feedback loop that adjusts weights based on downstream generation quality
- The three-stage pipeline is a natural extension of Task 13's wiki-read and wiki-search tools — T1 uses `wiki-read match-entities`, T2/T3 use `wiki-search`, T4 uses `wiki-read` to parse wikilinks
- The delta caching pattern aligns with the existing savepoint architecture — cache state can be saved/restored alongside story state
